# Hints: library.go.lemongrass

Template:  library
Language:  Go
Library:   lemongrass (https://github.com/mge1512/lemongrass)
Version:   0.1.1
Release:   1

`Version` is the version of the tool. `Release` counts the changes of this
file since `Version` was last set; a new version of the tool removes the
line.

lemongrass is a parser generator: the Lemon parser generator of SQLite with
a template for Go. It is a tool of the build. The parser that it writes
imports no package. Every statement in this file was run with lemongrass
0.1.0 and Go 1.24.7. lemongrass 0.1.1 has the same template and writes the
same parser file, byte for byte. Its generator has the new options
`--help` and `--version`, and the option `-x` prints the new version.

---

## Verified version and call

```
$ lemongrass -x
Lemon version 1.0
lemongrass version 0.1.1

$ lemongrass -q -l -T/usr/share/lemongrass/lempar.go grammar.y
```

- The call writes `grammar.go` beside `grammar.y`. The name of the parser
  file is the name of the grammar file with the suffix `.go`. With `-dDIR`
  the file goes to the directory DIR.
- `-T` names the template for Go, with its full path. The installed program
  does not look into `/usr/share/lemongrass`. Without `-T` it takes a file
  `grammar.lt` beside the grammar. Without that file it takes the C
  template `lempar.c` from the current directory, from the directory of the
  program or from a directory of `PATH`. It stops with an error when it
  finds none of them.
- `-q` stops the report file `grammar.out`.
- `-l` stops the `//line` directives. Without `-l` these directives have
  the file names of the call.
- With `-q -l` the only file name in the parser file is the name of the
  grammar file, as the call wrote it, in the first comment. Call lemongrass
  in the directory of the grammar file and with the bare file name. The
  parser file is then the same for every build, byte for byte.
- The exit status is 1 when the grammar has a conflict or an error. With a
  conflict lemongrass still writes the parser file. A build must stop on
  the status.
- The parser file has the line `// Code generated by lemongrass. DO NOT
  EDIT.` Do not edit it and do not run `gofmt` on it.

## The grammar file

A grammar file for Go, with the parts that most grammars need:

```
%name aqlParse
%token_prefix tok
%token_type {int}
%default_type {int}
%type negation {*node}
%extra_argument {*parseState}
%stack_size 0
%token LEFT RIGHT.
%include {
package aql
}
%syntax_error { yyarg.refused = true }
%parse_accept { yyarg.accepted = true }

statement ::= read end.
end ::=.
negation(A) ::= NOT negation(B). { A = &node{op: "not", kids: []*node{B}} }
```

- The code of `%include` starts with the package clause and the imports. A
  comment for the head of the file can stand before the package clause in
  this block.
- `%name` gives the first part of the function names. A name that starts
  with a small letter keeps the parser inside the package.
- The token numbers are constants in the parser file. Their names have the
  prefix of `%token_prefix`: `tokSELECT`, `tokWORD`. The number 0 is the
  end of the input and has no constant.
- A terminal symbol that no rule uses has no number. `%token NAME NAME.`
  gives it one. The parser then refuses it at every place.
- `%token_type` and the types of `%type` are Go types. `%default_type` is
  the type of every symbol without a `%type` line.
- `%extra_argument` has a type only. The code of the grammar reaches the
  value under the name `yyarg`.
- Each label of a rule is a local variable in the action. The action gives
  the label of the left side its value.
- A rule without an action gives its left side the value of the first
  symbol of its right side. This works only when the two symbols have the
  same type. Give every rule with an empty right side an action, and every
  rule whose first symbol has another type. Without one, the left side has
  the zero value or an old value of its type.
- In the code of `%syntax_error`, `yymajor` is the number of the token and
  `TOKEN` is its value.
- The names that start with `yy` belong to the parser and are names of the
  package. One package can have one parser from lemongrass.
- A raw string in a code block must not end with a backslash.

The Go template does not have these parts of Lemon:

| Part | What happens |
|---|---|
| `%destructor`, `%token_destructor`, `%default_destructor` | lemongrass reports an error. Go frees the values itself. |
| `%realloc`, `%free`, `%stack_size_limit`, option `-m` | lemongrass reports an error. |
| the error symbol in a rule, `%extra_context` | The Go compiler refuses the parser file. |

## Functions of the parser

With `%name aqlParse`:

| Function | Purpose |
|---|---|
| `aqlParseAlloc() *yyParser` | Make a parser |
| `aqlParse(p *yyParser, major int, minor aqlParseTOKENTYPE, arg aqlParseARGTYPE)` | Give the parser one token |
| `aqlParseFinalize(p *yyParser)` | Empty the stack of the parser |
| `aqlParseInit(p *yyParser)` | Put a parser back into its first state |
| `aqlParseTrace(trace func(msg string))` | Turn the trace messages on, or off with `nil`, for all parsers of the package |

`aqlParseTOKENTYPE` is the type of `%token_type`, and `aqlParseARGTYPE` is
the type of `%extra_argument`. There is no function that frees a parser.

## Run the parser

```go
st := &parseState{}
p := aqlParseAlloc()
defer aqlParseFinalize(p)
for i, t := range tokens {
	aqlParse(p, t.kind, i, st)
	if st.refused {
		return i // the first token that the parser refuses
	}
}
aqlParse(p, 0, 0, st) // 0 is the end of the input
if st.refused || !st.accepted {
	return len(tokens) // the input is not complete
}
```

- The parser runs the code of `%syntax_error` inside the call that brings
  the token it refuses. It never reports a token later.
- Stop at the first refused token. The parser drops that token and goes on.
  It can then run the code of `%parse_accept` for the rest of the input.
  "Accepted" is true only when no token was refused.
- For an input that is not complete, the call with 0 runs the code of
  `%syntax_error` and then the code of `%parse_failure`.
- After a refused token the parser reports the next one only after it has
  shifted three tokens. A second error message from one parser is therefore
  not reliable.
- `aqlParse` panics for a token number that is not a terminal symbol.

## Which tokens can come next

The parser has no function that says which tokens it accepts at a place. A
trial with a new parser gives the answer:

```go
// canComeNext says whether the kind can follow the tokens. The kind 0 is
// the end of the input. The parser accepts the tokens themselves.
func canComeNext(tokens []token, kind int) bool {
	st := &parseState{}
	p := aqlParseAlloc()
	defer aqlParseFinalize(p)
	for i, t := range tokens {
		aqlParse(p, t.kind, i, st)
	}
	aqlParse(p, kind, 0, st)
	if kind == 0 {
		return st.accepted && !st.refused
	}
	return !st.refused
}
```

The actions run in a trial too. Give each trial its own value for
`%extra_argument`, and let no action change anything else.

## The parser stack

- `%stack_size N` is the largest number of entries on the parser stack. The
  default is 100.
- A parser that needs more runs the code of `%stack_overflow` and empties
  its stack. The next token then looks like a syntax error, at a place
  where the input is correct.
- A rule that names itself at the end of its right side, like
  `negation ::= NOT negation.`, needs one entry for each token. Rules with
  an empty right side need entries too. With `%stack_size 8`, a grammar
  with five such symbols in one rule had a full stack for a correct input
  of four tokens.
- `%stack_size 0` means no limit. The stack is a slice and grows. Use it
  when the caller limits the number of tokens before the parser runs.
- In every other case give a limit above the largest need, and let the
  code of `%stack_overflow` set a flag that the caller reads.

## Compare the rules with a list

`lemongrass -g grammar.y` prints the rules of a grammar file without labels
and actions. It writes no parser file. The output has comment lines that
start with `//`, and one line for each rule:

```
statement ::= read end.
end ::=.
negation ::= NOT negation.
```

- lemongrass prints the rules that have an action first, and then the
  rules without an action. The order of the output is not the order of the
  file. Sort both lists before a comparison.
- To check the order of the rules, read it from the grammar file. This is
  simple when each rule stands on one line up to its period.

## Known gotchas

- No call without `-T`: lemongrass would write a parser in C code.
- No build without a check of the exit status: a grammar with a conflict
  still gives a parser file.
- No use of the default stack size for input of free length.
- No trust in `%parse_accept` after a refused token.
- No comparison of the `-g` output with a list in file order.
